# Module 1 — Core expressiveness

Reference notes for [module 1 of the plan](../plan.md#module-1--core-expressiveness). Examples are meant to be pasted into `cabal repl core` or evaluated with `-- >>>` comments. They deliberately avoid the functions you reimplement in the exercises.

## 1. Algebraic data types

A `data` declaration defines a new type as a **sum** (alternatives, `|`) of **products** (fields side by side).

```haskell
data Shape
  = Circle Double            -- radius
  | Rect Double Double       -- width, height
  deriving (Show, Eq)
```

- `Circle` and `Rect` are **constructors**, and constructors are ordinary functions: `:t Rect` gives `Double -> Double -> Shape`. So `map Circle [1, 2]` works.
- The number of values of a type follows the name: a sum *adds* possibilities, a product *multiplies* them. `Bool` has 2 values, `(Bool, Bool)` has 4, `Either Bool Bool` has 4, `Maybe Bool` has 3.
- `Maybe a = Nothing | Just a` and `Either e a = Left e | Right a` are just ADTs from the Prelude, not built-ins.

**Record syntax** names the fields and generates accessor functions:

```haskell
data Person = Person { name :: String, age :: Int } deriving Show

-- >>> age (Person "Ana" 30)
-- 30
-- >>> (Person "Ana" 30) { age = 31 }
-- Person {name = "Ana", age = 31}
```

Pitfall: a record field in a type with **several constructors** is a partial function. It crashes on a constructor that doesn't have that field. `-Wall` doesn't catch this, so prefer records only for single-constructor types.

**Recursive types** refer to themselves. This is how lists and trees are built:

```haskell
data Tree a = Leaf | Node (Tree a) a (Tree a)
```

The built-in list is the same idea with special syntax: `data [a] = [] | a : [a]`. `[1, 2, 3]` is sugar for `1 : (2 : (3 : []))`.

## 2. Pattern matching

A function can be defined by one equation per shape of its input. Patterns are tried **top to bottom** and the first match wins.

```haskell
area :: Shape -> Double
area (Circle r) = pi * r * r
area (Rect w h) = w * h
```

What patterns can contain:

| Pattern | Matches | Example |
| --- | --- | --- |
| Constructor | That constructor, binding its fields | `Just x`, `(x : xs)`, `[]` |
| Literal | That exact value | `0`, `'a'`, `"ok"` |
| Variable | Anything, binding it | `x` |
| Wildcard `_` | Anything, discarding it | `_` |
| Tuple | Tuples, element by element | `(a, _)` |
| As-pattern `@` | The whole value *and* its parts | `all@(x : _)` |
| Nested | Patterns inside patterns | `(Just (x : _))` |

```haskell
describe :: [Int] -> String
describe []                = "empty"
describe [x]               = "one: " ++ show x
describe whole@(x : _ : _) = "starts with " ++ show x ++ ", length " ++ show (length whole)
```

**Exhaustiveness.** With `-Wall`, GHC warns when a function doesn't cover every constructor (`-Wincomplete-patterns`). Treat that warning as an error in your head: a missing case is a runtime crash waiting to happen. `head []` crashing is the classic example of a partial function.

**Order matters.** A variable or `_` in the first equation shadows everything below it. GHC warns about this too (`-Woverlapping-patterns`).

## 3. Guards

Guards pick an equation by a boolean condition instead of by shape. `otherwise` is just `True`.

```haskell
classify :: Int -> String
classify n
  | n < 0     = "negative"
  | n == 0    = "zero"
  | even n    = "positive even"
  | otherwise = "positive odd"
```

Patterns and guards combine: match the shape first, then refine with guards. If every guard fails, matching falls through to the **next equation**.

## 4. `where`, `let` and `case`

All three introduce local definitions or branching. They differ in scope and in whether they're expressions.

| Construct | Is it an expression? | Scope | Typical use |
| --- | --- | --- | --- |
| `where` | No, it's attached to an equation | The whole equation, **including all its guards** | Helpers and names shared by several guards |
| `let … in …` | Yes | Only the `in` body | A local name in the middle of an expression |
| `case … of` | Yes | Each branch | Pattern matching on an intermediate value |

```haskell
bmi :: Double -> Double -> String
bmi weight height
  | v < 18.5  = "under"
  | v < 25    = "normal"
  | otherwise = "over"
  where
    v = weight / height ^ (2 :: Int)

firstWord :: String -> String
firstWord s = case break (== ' ') s of
  (w, _) -> w
```

Rule of thumb: `where` reads top-down ("the answer is X, where X means…") and is the default in most Haskell code. Use `let` when the name only makes sense inside one sub-expression. Use `case` when you need to match on something that isn't a function argument.

Pitfall: indentation is part of the syntax. Everything inside a `where`, `let` or `case` block has to line up in the same column.

## 5. Currying and partial application

Every Haskell function takes **exactly one argument**. `->` associates to the right, so

```haskell
add3 :: Int -> Int -> Int -> Int
-- is really
add3 :: Int -> (Int -> (Int -> Int))
```

and function application associates to the left: `add3 1 2 3` is `((add3 1) 2) 3`. Applying fewer arguments than the "full" count gives back a function. That's **partial application**:

```haskell
-- >>> :t add3 1
-- add3 1 :: Int -> Int -> Int
-- >>> map (add3 1 2) [10, 20]
-- [13,23]
```

This is why argument order matters when designing functions: put the argument that changes most often **last**, so partial application is useful. `Data.List`'s own functions follow this rule.

`curry` and `uncurry` convert between the curried form and the tuple form:

```haskell
-- >>> uncurry (+) (3, 4)
-- 7
```

## 6. Operator sections

Operators are functions written infix. Wrapping an operator in parentheses makes it prefix, and backticks make a named function infix:

```haskell
-- >>> (+) 2 3
-- 5
-- >>> 10 `div` 3
-- 3
```

A **section** fixes one side of an operator:

| Section | Means | Example |
| --- | --- | --- |
| `(x op)` | `\y -> x op y` | `(2 ^)` is "2 to the power of" |
| `(op y)` | `\x -> x op y` | `(^ 2)` is "squared" |

```haskell
-- >>> map (2 ^) [1, 2, 3]
-- [2,4,8]
-- >>> map (^ 2) [1, 2, 3]
-- [1,4,9]
```

Pitfall: `(- 1)` is **not** a section. It's the number minus one. Use `subtract 1` instead.

## 7. Composition, `$` and point-free style

**Composition** `(.) :: (b -> c) -> (a -> b) -> a -> c` chains functions right to left: `(f . g) x = f (g x)`.

**Application** `($) :: (a -> b) -> a -> b` is plain application with the **lowest precedence**, so it removes the need for parentheses to its right:

```haskell
-- These three are equivalent:
-- show (length (words "a b c"))
-- show $ length $ words "a b c"
-- (show . length . words) "a b c"
```

**Point-free** style defines a function without naming its argument (the "point"), by composing other functions:

```haskell
countWords :: String -> Int
countWords s = length (words s)   -- pointful
countWords   = length . words     -- point-free
```

When point-free helps:

- A pipeline of 2–4 transformations, each one a well-named function.
- Eta-reduction: `f x = g x` can become `f = g`.

When it hurts (sometimes called "pointless" style):

- It needs `flip`, `(.) . (.)`, or `uncurry` gymnastics to get there.
- The argument appears more than once, or in the middle of an expression.

The goal of the "three ways" exercise is to feel this boundary, not to make everything point-free. HLint's suggestions (shown inline by HLS) are a good second opinion.

## 8. List comprehensions

Borrowed from set-builder notation: generators (`<-`), filters (boolean expressions) and local `let`s.

```haskell
-- >>> [x * x | x <- [1 .. 10], odd x]
-- [1,9,25,49,81]
-- >>> [(x, y) | x <- [1 .. 3], y <- "ab"]
-- [(1,'a'),(1,'b'),(2,'a'),(2,'b'),(3,'a'),(3,'b')]
-- >>> [(a, b, c) | c <- [1 .. 20], b <- [1 .. c], a <- [1 .. b], a*a + b*b == c*c]
-- [(3,4,5),(6,8,10),(5,12,13),(9,12,15),(8,15,17),(12,16,20)]
```

- Later generators vary **faster**, like nested loops.
- A pattern on the left of `<-` silently **skips** elements that don't match: `[x | Just x <- [Just 1, Nothing, Just 3]]` is `[1, 3]`.
- Every comprehension can be rewritten with `map`, `filter` and `concatMap`. Once you've done the `map` and `filter` exercises, try translating the examples above by hand. Module 6 shows that comprehensions are really the list monad.

## 9. `data`, `newtype` and `type`

| | `type` | `newtype` | `data` |
| --- | --- | --- | --- |
| Creates a new type? | No, only an alias | Yes | Yes |
| Type-checker distinguishes it from the original? | No | Yes | Yes |
| Constructors and fields | None | Exactly 1 constructor with exactly 1 field | Any |
| Runtime cost | None | None, erased after type-checking | A box per value |
| Can have its own instances? | No | Yes | Yes |
| Laziness | Same as the original | Matching never forces anything | Matching forces the constructor |

```haskell
type Name = String                 -- documentation only; any String fits
newtype Email = Email String       -- a String the compiler won't mix up with Name
data Contact = Contact Name Email  -- a new structure
```

- Use `type` to shorten long signatures or document intent. It adds no safety at all.
- Use `newtype` to get safety at zero cost, and to give an existing type a different instance. That second use is the core of module 3 (`Sum`, `Product`, `Min`…).
- Use `data` for everything else.

## 10. Recursion and folds

Recursion on lists usually follows the shape of the type: one equation for `[]` (base case) and one for `x : xs` (recursive case).

```haskell
sumList :: [Int] -> Int
sumList []       = 0
sumList (x : xs) = x + sumList xs
```

Many functions share this exact skeleton and differ only in two places: **the value for `[]`** and **how to combine `x` with the result for `xs`**. `foldr` is that skeleton with those two places turned into parameters:

```
foldr f z [x1, x2, x3]  =  x1 `f` (x2 `f` (x3 `f` z))
```

In other words, `foldr f z` replaces every `:` with `f` and the final `[]` with `z`.

### `foldr` versus `foldl`

```
foldr f z [x1, x2, x3]  =  f x1 (f x2 (f x3 z))     -- associates to the right
foldl f z [x1, x2, x3]  =  f (f (f z x1) x2) x3     -- associates to the left
```

| | `foldr` | `foldl` |
| --- | --- | --- |
| Associates | Right | Left |
| Works on infinite lists? | Yes, if `f` is lazy in its second argument | Never, it has to reach the end first |
| Accumulator position in `f` | Second argument | First argument |
| Typical use | Building structures, short-circuiting | Almost never in practice. Use `foldl'` (module 8) |

`foldr` can stop early on an infinite list because `f` receives the rest of the fold **unevaluated**. If `f` doesn't need it, it's never computed:

```haskell
-- >>> foldr (\x acc -> x > 10 || acc) False [1 ..]
-- True
```

`foldl` has no such escape hatch, and on large finite lists it builds a chain of unevaluated thunks. That's the space leak you'll provoke on purpose in module 8.

### The universal property of `foldr`

This is the formal version of "same skeleton, two holes". For a function `g` on lists:

```
g []       = z
g (x : xs) = f x (g xs)
```

holds **if and only if** `g = foldr f z`.

In practice this is a recipe for the "three ways" exercise:

1. Write the explicit-recursion version.
2. Read off `z` from the `[]` equation.
3. Read off `f` from the `x : xs` equation, by replacing the recursive call `g xs` with a variable (say `acc`).
4. That gives `g = foldr f z`, and the property guarantees it's the same function.

Applied to `sumList` above: `z = 0` and `f x acc = x + acc`, so `sumList = foldr (+) 0`.

Some functions don't fit the skeleton directly: they need an extra argument, look at two elements at a time, or stop in the middle. Those are the interesting cases in the exercise. Try it anyway before giving up, because `foldr` can build a *function* as its result, not only a value.
