# Module 4 — Functor and Foldable

Reference notes for [module 4 of the plan](../plan.md#module-4--functor-and-foldable). Examples are meant to be pasted into `cabal repl core` or evaluated with `-- >>>` comments; `Functor` and `Foldable` are in the `Prelude`, and `void` and `$>` come from `Data.Functor`. Outputs and compiler messages were checked with GHC 9.10.3. The notes explain the ideas; the instances and the file system are yours to write.

## 1. Kinds: the types of types

Values have types, and types have **kinds**. `:k` in GHCi shows them:

```
Int :: *
Maybe :: * -> *
Maybe Int :: *
Either :: * -> * -> *
Either String :: * -> *
(,) :: * -> * -> *
(->) :: * -> * -> *
```

- `*` is the kind of types that have values: `Int`, `Maybe Int`, `String -> Bool`.
- `Maybe` alone has no values. It is a **type constructor**, a function on types: give it a `*` and it gives back a `*`.
- Type constructors are curried like functions (module 1, section 5). `Either String` is `Either` with one argument applied, and is itself of kind `* -> *`.

Classes have kinds too. `Semigroup` and `Monoid` are about types of kind `*`; `Functor` is about type constructors:

```
Functor :: (* -> *) -> Constraint
```

So `instance Functor Int` cannot even be written, and the kind checker says so before anything else:

```
error: [GHC-83865]
    • Expected kind ‘* -> *’, but ‘Box’ has kind ‘*’
    • In the first argument of ‘Functor’, namely ‘Box’
      In the instance declaration for ‘Functor Box’
```

## 2. `Functor`: mapping inside a structure

```haskell
class Functor f where
  fmap :: (a -> b) -> f a -> f b
  (<$) :: a -> f b -> f a
  {-# MINIMAL fmap #-}
```

`fmap` applies a function to every `a` inside an `f a` and **keeps the structure**: the same constructors, in the same places, with the same number of elements. For lists, `fmap` is `map`.

- `<$>` is `fmap` as an operator: `(+ 1) <$> Just 2` gives `Just 3`.
- `x <$ fa` replaces every element by `x`: `0 <$ Just 'x'` gives `Just 0`.
- From `Data.Functor`: `void` replaces every element by `()` (`void (Just 3)` gives `Just ()`), and `$>` is `<$` flipped (`Just 3 $> "y"` gives `Just "y"`).

**The laws.**

- **Identity:** `fmap id == id`.
- **Composition:** `fmap (g . f) == fmap g . fmap f`.

Together they say that `fmap` changes the elements and nothing else. The type checker cannot enforce them. This instance compiles, and breaks identity:

```haskell
data Pair a = Pair a a deriving Show

instance Functor Pair where
  fmap f (Pair a b) = Pair (f b) (f a)
```

```
-- >>> fmap id (Pair 1 2)
-- Pair 2 1
```

In Haskell, the second law follows from the first: from the type of `fmap` alone, any `fmap` that keeps `id` also keeps composition (Wadler, "Theorems for free!"; section "Further reading"), leaving aside `undefined` and `seq`. A broken composition law therefore always comes with a broken identity, but testing both costs nothing and the failing one points at the mistake.

## 3. The functors in `base`

To make an instance, a type must have kind `* -> *`. A type with two parameters becomes a functor by **fixing the first one**, and `fmap` then maps over the last:

| Type | Kind | `fmap f` does | Example |
| --- | --- | --- | --- |
| `Maybe` | `* -> *` | applies `f` inside `Just`, leaves `Nothing` | `fmap (+ 1) (Just 2)` gives `Just 3` |
| `[]` | `* -> *` | `map f` | |
| `Either e` | `* -> *` | applies `f` inside `Right`, leaves `Left` alone | `fmap (+ 1) (Left "no")` gives `Left "no"` |
| `(,) a` | `* -> *` | applies `f` to the second component | `fmap (+ 1) ("label", 2)` gives `("label",3)` |
| `(->) r` | `* -> *` | composes: `fmap f g` is `f . g` | `fmap (+ 1) (* 2) 5` gives `11` |

Writing `instance Functor Either` fails because of the kind (here on a local copy of `Either`, since `base` already has the `Either e` instance):

```
error: [GHC-83865]
    • Expecting one more argument to ‘Either’
      Expected kind ‘* -> *’, but ‘Either’ has kind ‘* -> * -> *’
    • In the first argument of ‘Functor’, namely ‘Either’
      In the instance declaration for ‘Functor Either’
```

Points worth noticing:

- **Only the last parameter is mapped.** `Either e` treats `Left` as "stop here": an error carried along untouched. That is why `Either` is the usual type for computations that can fail with a reason, in modules 5 and 6.
- **The first component of a pair is context.** A pair `(label, value)` is a value with something attached, and `fmap` keeps the attachment.
- **The function functor.** `(->) r` is "a value that is still waiting for an `r`". Mapping over it can only mean doing something to the result once it comes, which is composition. Module 6 turns this into the `Reader` monad.

## 4. `Foldable`: everything from `foldMap`

```haskell
class Foldable t where
  foldMap :: Monoid m => (a -> m) -> t a -> m
  foldr   :: (a -> b -> b) -> b -> t a -> b
  -- and toList, null, length, elem, sum, product, maximum, minimum, ...
  {-# MINIMAL foldMap | foldr #-}
```

Module 3 used `foldMap` on lists. `Foldable` is the class of every structure it works on, and one method is enough: everything else has a default.

- `length` is `getSum . foldMap (const (Sum 1))`.
- `sum` is `getSum . foldMap Sum`, `product` the same with `Product`.
- `elem x` is `getAny . foldMap (Any . (== x))`.
- `toList` is `foldMap (\x -> [x])`.
- `foldr` comes from `foldMap` through `Endo`: each element becomes the function `f x`, and composing them all and applying the result to `z` is `foldr f z`.

  ```haskell
  foldr f z t = appEndo (foldMap (Endo . f) t) z
  ```

This is why module 3 built the newtypes: they are the vocabulary in which a `Foldable` instance answers questions.

**Surprises from the `base` instances.** `Foldable` sees only the elements of the last parameter, the same ones `fmap` maps:

```
-- >>> length ("label", 2)
-- 1
-- >>> sum ("x", 5)
-- 5
-- >>> length (Left "abc" :: Either String Int)
-- 0
-- >>> elem 3 (Just 3)
-- True
```

A pair holds one element, and a `Left` holds none.

**Partial methods.** `maximum`, `minimum`, `foldr1` and `foldl1` have no answer for an empty structure, and fail at runtime:

```
-- >>> maximum ([] :: [Int])
-- *** Exception: Prelude.maximum: empty list
```

They are exactly the folds whose monoid has no identity: `Max` is only a semigroup for unbounded types (module 3, section 3). `foldMap (Just . Max)` is the total version.

## 5. Trees

Two shapes recur through the plan:

```haskell
-- A binary tree: empty, or a value with a left and a right subtree.
data Tree a = Leaf | Node (Tree a) a (Tree a)

-- A rose tree: a value and any number of children.
data Rose a = Rose a [Rose a]
```

Both have kind `* -> *`, and both are functors and foldables.

- **`fmap` on a tree keeps the shape.** Every `Node` stays a `Node` with the same children; only the values change.
- **`Rose` holds a list of `Rose`s.** Its `fmap` maps every child, which is the list's `fmap` applied to the tree's `fmap`. Its `foldMap` folds every child and combines the results, which is the list's `foldMap`, again with the tree's inside.
- **`foldMap` chooses an order.** A binary tree can be folded in order (left, value, right), pre-order (value first) or post-order. `sum` and `length` do not care, since `Sum` is commutative. `toList`, `First` and `Last` do: they show the order you picked. For `Node (Node Leaf 1 Leaf) 2 (Node Leaf 3 Leaf)`, in order gives `[1,2,3]` and pre-order `[2,1,3]`.

**Deriving.** `DeriveFunctor` and `DeriveFoldable` write both instances for you. They are not in Haskell 2010, which this repository uses, so without the extension:

```
error: [GHC-86639]
    • Can't make a derived instance of ‘Functor Tree’:
        You need DeriveFunctor to derive an instance for this class
```

The derived `foldMap` visits fields left to right as they are declared: for `Node (Tree a) a (Tree a)` that is in order, and for `Rose a [Rose a]` it is pre-order. The rose tree `Rose 1 [Rose 2 [Rose 4 []], Rose 3 []]` folds as `[1,2,4,3]`.

## 6. Testing functor laws

The laws quantify over structures **and functions**: `fmap (g . f) == fmap g . fmap f` for every `f` and `g`. Two things are new compared with module 3.

- **Generating structures.** A tree generator that picks `Node` or `Leaf` at random can run forever, or build trees too big to be useful. `listOf` faced the same problem with lengths and fixed it with a bound. A tree needs a bound too: on its depth, on its size, or by building it from a generated list.
- **Generating functions.** `Gen (Int -> Int)` is just a generator whose values are functions, like the one in the `Arbitrary (Endo a)` instance of exercise 3. Functions have no `Show`, so `forAll` cannot report them; the `Shown` newtype in `test/core/M03/MonoidsSpec.hs` is one way around it.

For `(->) r`, the structures are themselves functions, so the two sides of a law are compared by applying them to a generated argument, as `Endo` was in module 3.

## 7. A file system as a rose tree

The mini-project models a directory tree in memory:

```
/
├── notes.md        (120 bytes)
├── src/
│   ├── Main.hs     (800 bytes)
│   └── Lib.hs      (2400 bytes)
└── empty.txt       (0 bytes)
```

Directories have children and files do not, so the shape is a rose tree. With `Foldable`, every question that looks at entries one at a time is a `foldMap` into the right monoid:

| Question | Monoid |
| --- | --- |
| total size | `Sum` |
| number of files | `Sum`, counting 1 per file and 0 per directory |
| largest file | `Maybe (Max …)`: there may be no file at all |
| is any file empty? | `Any` |
| first file in traversal order | `First` |
| several of these in one pass | a tuple of them (module 3, section 4) |

Some questions do not fit: an entry's **full path** depends on the directories above it, and `foldMap` only ever sees one entry at a time. `fmap` cannot help either, for the same reason. Deciding where those questions go is part of the exercise.
